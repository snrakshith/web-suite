### 1. Single Responsibility Principle (SRP)

**Core Idea:**  
The Single Responsibility Principle (SRP) states that a component should have only one reason to change. This means a component should do only one thing and do it well. If a component is responsible for multiple tasks, it becomes harder to maintain and understand.

**Example Recap:**

- **Component:** `UserProfile`
- **Separate Responsibilities:** `UserInfo` (display user data), `AuthStatus` (handle authentication status)

In this example, instead of having `UserProfile` handle both user data display and authentication status, we split these responsibilities into separate components (`UserInfo` and `AuthStatus`).

**Simplified Understanding:**  
SRP ensures that each component has a clear, single purpose. If something needs to change (e.g., how user info is displayed), only the `UserInfo` component is affected, not the `AuthStatus`.

### 2. Interface Segregation Principle (ISP)

**Core Idea:**  
The Interface Segregation Principle (ISP) suggests that a client (a component or a module) should not be forced to depend on interfaces (or props) it doesn't use. Instead of having one large interface, it's better to have multiple smaller, more specific interfaces.

**Example Recap:**

- **Base Interface:** `WidgetProps` (general properties for a widget)
- **Specific Interfaces:** `UserWidget` (depends on `userName` prop), `WeatherWidget` (depends on `temperature` prop)

In this example, instead of forcing all widgets to accept all possible props (e.g., userName, temperature), each widget component only depends on the props it actually uses.

**Simplified Understanding:**  
ISP ensures that components are only exposed to the data and functions they need. This makes the components easier to maintain and avoids unnecessary complexity.

### 3. Dependency Inversion Principle (DIP)

**Core Idea:**  
The Dependency Inversion Principle (DIP) states that high-level modules should not depend on low-level modules; both should depend on abstractions. In other words, instead of hardcoding dependencies, you should rely on interfaces, abstract classes, or contexts.

**Example Recap:**

- **High-Level Component:** `DataDisplay`
- **Abstracted Dependency:** `useDataFetcher` hook (handles data fetching)

In this example, `DataDisplay` doesn't directly handle data fetching. Instead, it relies on the `useDataFetcher` hook. If the data-fetching logic changes, only the hook needs to be updated, not the `DataDisplay` component.

**Simplified Understanding:**  
DIP ensures that components are flexible and decoupled from specific implementations. This makes it easier to swap out or update dependencies without affecting the rest of the code.

### Summary of All Principles

1. **Liskov Substitution Principle (LSP):**

   - **Focus:** Ensure that derived components can replace their base components without breaking the application.
   - **Simplified:** New components should behave like the original ones when substituted.

2. **Open/Closed Principle (OCP):**

   - **Focus:** Extend components by adding new functionality without modifying existing code.
   - **Simplified:** Add new features by creating new components, not by changing existing ones.

3. **Single Responsibility Principle (SRP):**

   - **Focus:** Ensure each component has only one reason to change by giving it a single responsibility.
   - **Simplified:** Each component should do one thing well.

4. **Interface Segregation Principle (ISP):**

   - **Focus:** Ensure components depend only on the interfaces they actually use, avoiding unnecessary dependencies.
   - **Simplified:** Break down large interfaces into smaller, more specific ones.

5. **Dependency Inversion Principle (DIP):**
   - **Focus:** Depend on abstractions rather than specific implementations to keep components decoupled and flexible.
   - **Simplified:** Use hooks, contexts, or abstract classes to handle dependencies, making components easier to change or extend.
